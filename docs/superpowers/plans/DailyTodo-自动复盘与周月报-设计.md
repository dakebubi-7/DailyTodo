# DailyTodo 自动复盘与周/月报 — 设计文档

> 本文整理自 2026-06-03 的一次设计讨论，把"让应用自动生成复盘 / 明日待办 / 可复用知识，以及周报、月报"这个需求，从底层引擎一路梳理到产品形态。
> **定位**：需求与设计蓝图，不是实现说明。真要开发时，这份文档基本就是需求清单。
> **核心矛盾**（贯穿全文）：复盘需要"理解"，只有 LLM 能写得有意义；而"理解无法外包"——AI 产出的是草稿，署名交出去的内容仍需用户把关。

---

## 0. 问题起点

现在 `logs/daily/YYYY-MM-DD.md` 由 DailyTodo 应用写入（带 `<!-- DAILYTODO:... -->` 标记的「今日工作 / 灵感闪念 / 每日任务」），但底部的「复盘 / 明日待办 / 可复用知识」只是**空模板**，没人填。

**目标**：让应用在写完每日文件后，自动补齐这三段；并把周报、月报也自动化。

**关键约束**：DailyTodo 应用跑在 Claude Code 之外，Claude 的 hook 捕捉不到外部应用写文件。所以真正可行的链路是 **应用同步完 → 调本地脚本 → 脚本调 LLM → 回填**。

---

## 1. 整体链路

```
DailyTodo 应用同步完成
   └─ 写完 logs/daily/YYYY-MM-DD.md（工作/灵感/任务）
   └─ subprocess 调 review 脚本（应用里加一行）
          └─ 读当天已完成任务/工作/灵感
          └─ 拼 prompt，调 OpenAI 兼容 API（base_url + key + model 走环境变量）
          └─ 把「复盘 / 明日待办 / 可复用知识」回填到当天文件对应段落
```

设计选型（讨论已确认）：

| 维度 | 选择 |
|------|------|
| 生成方式 | AI 复盘代理（非确定性段落需要推理） |
| 写入位置 | 回填当天 daily 文件 |
| 触发方式 | 应用写完后调用脚本（+ 定时器兜底，见 §3） |
| LLM 接口 | OpenAI 兼容（base_url + key + model，可换 DeepSeek / Claude / 本地模型） |
| 周 / 月报 | 都要 |

---

## 2. 引擎设计：三个核心要点

### 2.1 回填靠"锚点标记"，不靠纯文本替换

应用现在写的是裸标题 `## 复盘`。脚本要稳定、幂等地回填，应让应用把这些段落用标记包起来：

```markdown
<!-- DAILYTODO:REVIEW:START -->
## 复盘
<!-- DAILYTODO:REVIEW:END -->
```

脚本**只替换 START/END 之间的内容** → 重复跑不会越填越乱，也不动应用自己的工作/任务段落。标记是 HTML 注释，在 Obsidian 渲染时**不可见**。

AI 写入段落时必须带状态元数据，例如：

```markdown
<!-- DAILYTODO:REVIEW:START -->
<!-- DAILYTODO:AI_HASH:sha256:xxxx -->
🤖 AI 草稿
今天完成了……
<!-- DAILYTODO:REVIEW:END -->
```

Hash 基于“去掉 Hash 行后的实际正文”计算，用来区分“未被用户动过的 AI 草稿”和“用户微调后的成果”。此外支持显式冻结标签（如 `<!-- DAILYTODO:FREEZE -->`）：一旦冻结，补偿扫描和批量生成都必须跳过，除非用户通过 UI/命令明确解冻。

### 2.2 段落分两类，别都丢给 AI

| 类型 | 例子 | 谁来写 |
|------|------|--------|
| `deterministic` | 「明日待办」中的**未完成任务结转** | 程序逻辑（应用已在做"继承自"） |
| `ai` | 「复盘」「可复用知识」「建议性待办」 | LLM + prompt |

「明日待办」最干净的做法：应用先确定性填结转任务，AI 只在后面追加建议。

### 2.3 数字靠程序数，不靠 AI 编

涉及量化（完成 X 项、连续 Y 天）时，由程序统计（数勾选数、数天数），AI 只负责组织语言。
（呼应现有周复盘里的原则：*"不 invent 数字统计"*。）

## 3. 健壮性：关机 / 软件关闭也要"第二天打开就能看到"

**核心思路：不依赖“那一刻在线”，依赖“下次上线自动补”；但补偿扫描必须用状态机判断，不能只靠模糊判空。**

把脚本做成 **「扫描 + 补全」** 模式，而非“只处理今天”：每次运行往回扫最近 N 天的 daily 文件，凡是复盘段落处于 `Unprocessed` 或允许安全更新的状态就补生成。

补偿扫描判定规则：

1. START/END 之间没有任何内容（或只有空行）→ `Unprocessed`，执行补全。
2. 包含 `AI_HASH` → 重新计算“去掉 Hash 行后的正文 Hash”。
   - Hash 一致：用户从未动过这段 AI 草稿，视为 `AI_Unmodified`，可按策略覆盖/更新。
   - Hash 不一致：用户手动微调过，视为 `User_Modified`，跳过且绝不覆盖。
3. 没有 `AI_HASH` 且有内容 → 视为用户纯手写，跳过且绝不覆盖。
4. 存在显式冻结标签 → 无条件跳过，除非用户明确解冻。

“强制重新生成”必须是显式动作，例如按钮或命令；后台补偿扫描不得擅自覆盖用户改过的成果。

| 场景 | 处理 |
|------|------|
| 今天没关机 | 定时器（如 23:00）跑完；Obsidian 监听文件变化会**自动刷新**已打开的笔记 |
| 今天关机了，次日开机 | 应用**开机自启** → 启动第一件事跑补偿扫描 → 补昨天 → 打开 Obsidian 已就绪 |
| 连续几天没开机 | 回来一次性补齐这几天（幂等：已填的跳过） |

**双保险**：定时器定点跑 + 应用启动时补偿扫描。Windows 任务计划程序有"错过计划开始时间后尽快运行"选项，专门补关机错过的那次。

> 判断“这段是否为空”不能靠肉眼文本判定，必须使用 `AI_HASH`、正文 Hash、冻结标签与“无 Hash 有内容 = 用户手写”的状态机。

## 4. 模板适配：让一套引擎吃所有人的模板

引擎**不认识任何段落名**，只读配置干活。换人 = 换配置 + 模板里埋好标记，引擎一行不改。

### 4.1 配置驱动（base 示例）

```yaml
sections:
  - marker: UNFINISHED      # 「整理未完成」
    type: deterministic
  - marker: TOMORROW        # 「明日要完成」
    type: ai
    prompt: "根据今天进度，列出明天要完成的事"
  - marker: NEXT_STEP       # 「下一步」
    type: ai
    prompt: "指出当前卡点的下一步动作"
  - marker: SUMMARY         # 「今日总结」
    type: ai
    prompt: "总结今天做了什么、收获是什么"
```

中文/英文、四段/五段、要不要 AI，全由配置 cover。

### 4.2 契约：标记 + 配置

```
通用引擎（代码，所有人共用，永不改）
   + 我的模板（埋我的标记） ⇄ 我的 config
   + 他的模板（埋他的标记） ⇄ 他的 config
```

- **标记**定"填哪里"；**配置**定"填什么 + 怎么提示"。两者彻底解耦。
- 退化兜底：某人不愿埋标记 → 引擎按标题文字匹配（配置里写死标题名）。能用，但标题一改/一翻译就断，所以**标记才是稳的契约**。

## 5. 三种产物对照表

日复盘、个人周复盘、对外工作周报是同一套引擎，输入源与输出模板不同。

| | 日复盘 | 个人周复盘 | 对外工作周报 / 月报 |
|---|---|---|---|
| 触发 | 应用每天同步后 | 每周日（定时 / 手动） | 每周 / 每月底（定时 / 手动） |
| 输入 | 当天 daily 文件 | 本周 7 个 daily + 日复盘 | 显式标记为 `type: work` 的工作数据 + 公司模板 |
| 输出 | 回填当天文件 | `logs/weekly-review/YYYY-Wxx.md` | `exports/weekly-reports/YYYY-Wxx.md` / `exports/monthly-reports/YYYY-MM.md` |
| 模板 | 用户自己的 | 用户自己的 | **公司规定的**（可导入） |
| 语气 | 随意 | 随意 | **正式** |
| 内容范围 | 全量 | 全量 | **只抽工作白名单内容，默认排除 private/secret/灵感等私人段落** |
| 量化数字 | — | 程序统计 | 程序统计（不让 AI 编） |

**对外周报/月报特殊处理**：

1. **公司模板可导入** —— 粘贴公司格式 → AI 认结构 → 用本周/本月数据填。
2. **路径物理隔离** —— 对外产物一律写入 `exports/weekly-reports/`、`exports/monthly-reports/`，不得与个人 `logs/` 复盘混放。
3. **物理脱敏** —— 程序层默认剔除 `tag: private`、`tag: secret` 或特定私人段落（如“灵感闪念”），只允许显式标记为 `type: work` 的内容进入 `exports/`。这是一道硬规则：即使 AI 脱敏失败，也不能突破。
4. **强调草稿** —— 交给领导前必须自己过一遍，留好编辑入口。
5. 月报、季度、年度同理：引擎不变，时间窗和输入源变大，但对外目录和脱敏规则不变。

> 周复盘模板已有现成结构可参考：2026-W21 周知识复盘。

## 6. 产品化：让大众好上手

**核心思路**：底层（标记 + 配置 + 补偿 + 定时）负责"跑得稳"；UI 层负责"人人会用"。两层之间靠应用把 UI 选择**翻译**成底层配置。用户永远不直接编辑 yaml / 标记 / 任务计划程序。

### 6.1 底层概念 → UI 翻译表

| 底层 | 用户在 UI 看到的 | 应用背后偷偷做的 |
|------|------------------|------------------|
| config 段落 | 「日记模板」编辑器，勾选/拖拽段落 | 生成 yaml |
| `<!-- MARKER -->` | **完全看不到** | 写模板时自动埋 |
| `type: ai/deterministic` | 每段下拉：「AI 自动写 / 我自己写 / 自动结转任务」 | 写进配置 |
| prompt | 高级里才有，普通人用默认 | 预置 prompt |
| 定时器 | 开关 + 时间：「每晚 23:00 自动生成 ✓」 | 注册系统定时任务 |
| 关机补偿 | 不暴露，默认开 | 启动时自动跑 |
| LLM key | 「设置 → AI」一个框 / 选预置 | 存起来调 API |

### 6.2 三个产品设计原则

1. **分层（渐进式披露）**：90% 的人用预设模板，点开关即用；10% 的人才进「高级设置」改 prompt、改时间。
2. **默认值装完即用**：什么都不配也能跑（默认模板 + 默认每晚生成 + 补偿默认开）。配置是用来"改"的，不是用来"开"的。
3. **首次启动 30 秒向导**：选模板 → 设时间 → 选 AI，完事。

### 6.3 API Key —— 唯一绕不开要用户掏东西的地方（三档，越往下越好上手）

1. **完全免登录：用户自己填 key**（最省开发，劝退小白）：支持环境变量、本地配置文件，数据与调用都由用户自己负责。
2. **免登录但半引导：应用预置选项**（DeepSeek/Claude），引导去官网拿 key（半懂的人能搞定），本质仍然是用户自填 key。
3. **登录后 SaaS 代付**：后台用应用方 key，给免费额度/订阅；用户不碰 key，但必须轻量登录（微信/GitHub/邮箱等）换取带配额限制的 App-Token。

边界必须清楚：**完全免登录状态不能提供匿名无限代付接口**。否则无法识别免费额度/订阅状态，也无法防止刷量脚本薅空成本。

## 7. 小白用自己的模板（且不想学）

**核心解法**：不让用户适应系统，让 AI 去适应用户的模板——把"加标记、写配置"从用户的作业变成 AI 的活儿。

### 7.1 主路径：让 AI 认模板（一次性）

```
用户保留自己的模板（整理未完成 / 明日要完成 / 下一步 / 今日总结）
   ↓ 应用把模板丢给 LLM 读一遍
AI：「我看懂了你这 4 段，打算这样处理 —— 整理未完成=自动搬任务，其余=AI 生成。对吗?」 [对] [我改一下]
   ↓ 用户点「对」（大白话确认，零术语）
应用背后：偷偷埋标记 + 生成配置
```

用户感觉"我用的还是自己的模板"（视觉没变，标记不可见）。**用 LLM 自己打通"自由模板 → 结构化配置"这道坎。**

### 7.2 认错 / 微调（零术语）

- 选中某段 → 右键「这段让 AI 写复盘」。
- 或每段一个标签 `[AI写] [我自己写] [搬任务]`，点一下切换。

### 7.3 更省事的两条路

- **模糊匹配**：内置近义词词典（复盘/总结/回顾 → 复盘段；明日/待办/计划 → 待办段），用户啥都不做应用自己猜（最好配一句确认兜底）。
- **拿旧日记当样板**：丢一篇旧日记进来，AI 反推结构。

### 7.4 认不出也别崩（优雅降级）

把生成的复盘**追加到文件末尾** + 一句："我没完全认出你的模板，先放这儿了，点这里告诉我该放哪。" **永远不让"看不懂模板"变成"用不了软件"，绝不乱覆盖。**

## 8. 预设之上的局部修改（继承 / 覆盖）

用户选了预设，但想单独改几个点 —— 用 **"预设 + 覆盖(override)"** 模式，不是重做模板。

**用户视角**：每段一行 + 几个小控件：
```
复盘        [AI写 ▼] [详细 ▼] ↑↓ ✓显示
明日待办     [AI写 ▼] [简洁 ▼] ↑↓ ✓显示
可复用知识   [我自己写 ▼]      ↑↓ ✗隐藏   ← 关掉
+ 加一段…
```

- 改 prompt 对小白：不给文本框，给**旋钮**（长度：简短/适中/详细；语气：口语/正式；形式：叙述/要点）。进阶才给可选输入框追加一句自定义要求。

**技术关键（用户无感）**：预设 = base 配置，用户改动只存一层 override 叠上去。好处：

1. 预设升级时，没改过的部分自动跟着升级，改过的保留。
2. 随时「恢复默认」（清空 override）。
3. 用户感觉只动了几个点，没接管整个模板。

## 9. 登录：渐进式，永不阻挡首次使用

**登录是手段不是目的。它的必要性完全跟着"API key 怎么解决"走。**

| | 不需要登录 | 需要登录 |
|---|---|---|
| 形态 | 本地个人工具、用户自填 key、数据全在本地 | 代付/SaaS、云同步、多设备、团队/分享周报、订阅收费 |

**两个提醒**：

- 日记类应用 **local-first（免登录）反而是信任卖点**——很多人不想让私人日记进别人服务器。
- 别混淆 **云账号登录**（联网/服务器/同步）和 **本地密码锁**（防同台电脑别人翻日记，不联网无账号）。日记应用很可能只需要后者。

**采用渐进式（已确认方向）**：

```
默认：免登录，本地完整可用（用户自填 key / 环境变量 / 本地配置 / 本地锁）
   ↓ 只有用户主动要这些功能时，登录才出现
云同步 / 多设备 / 代付AI / 团队周报 → 「登录解锁」
```

**关键边界**：

- 免登录不是“匿名使用应用方云端额度”。免登录时只能使用用户自己的 API Key 或本地模型。
- SaaS 代付/免费额度必须轻量登录，服务端签发 App-Token，并绑定配额、速率限制、订阅状态和可撤销凭证。
- 登录不是为了查看日记。日记仍在本地；登录只负责给“本地调用云端 AI 算力”做账单鉴权。
- **首次使用绝不卡登录墙**——登录是“解锁高级功能的钥匙”，不是“进门的门槛”。

## 10. 文件写入与同步盘安全约束

DailyTodo 的目标使用环境是 Obsidian Vault，本质是一组本地 Markdown 文件。很多用户会同时使用 Syncthing、iCloud、Git、坚果云或其他同步工具。后台补偿扫描如果批量改写过去几天的 `*.md`，而同步盘此时正在拉取云端更新，就可能产生同步冲突副本，甚至覆盖用户刚同步下来的内容。

因此，回填脚本必须遵守 **原子化写入与文件锁（Atomic Write & File Lock）** 约束：

1. **禁止直接覆盖写**：不得直接 `open(file, 'w')` 写回原 Markdown 文件。
2. **读取时记录文件状态**：读取原文件后，记录文件大小与修改时间（必要时可加内容 Hash）。
3. **临时文件中完成替换**：在系统临时目录中生成临时文件，例如 `YYYY-MM-DD.md.tmp`，只在临时文件内完成 START/END 锚点内容替换。
4. **写入前二次检查**：真正写回前，再次检查原文件大小与修改时间。若脚本读取后文件被 Obsidian、同步盘或其他进程修改过，必须放弃本次写入并报错/稍后重试，不能强行覆盖。
5. **操作系统原子替换**：通过 OS 原子替换能力（如 Python `os.replace()`）瞬间替换原文件，降低半写入、断电、同步盘扫描中的损坏概率。
6. **批量扫描保守执行**：补偿扫描对多个文件操作时，应单文件串行处理；遇到冲突文件直接跳过并记录，不做破坏性重试。

这条约束和 `AI_HASH` 状态机同等重要：前者防“外部进程/同步盘冲突”，后者防“用户微调内容被误刷”。

## 11. 一句话总结
