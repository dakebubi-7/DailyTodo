# DailyTodo 多对话协作使用说明

## 相关文件

- 快速上手：`G:\Personal-AI\DailyTodo\app\docs\DailyTodo-多对话快速上手.md`
- 提示词合集：`G:\Personal-AI\DailyTodo\app\docs\DailyTodo-各部门提示词合集.md`

## 1. 这套对话是干什么的

这些对话不是 13 个同时开工的程序员，而是 **13 个分工明确的顾问 / 执行者**。

它们共用同一个项目目录：

- `G:\Personal-AI\DailyTodo\app`

所以正确用法是：

```text
项目总控负责分派任务
各部门负责分析 / 执行小范围任务
每个部门结束后把摘要交回项目总控
项目总控决定下一步
```

---

## 2. 最重要的原则

### 原则 1：项目总控永远是中心

推荐流程：

```text
项目总控
  ↓
产品PMO / 工程效能部 / 验证部 / 前端部 / 其他专业部门
  ↓
各部门输出摘要
  ↓
回到项目总控
  ↓
项目总控决定下一步
```

### 原则 2：不要多个部门同时改代码

可以多个部门同时做“只读分析”，但 **同一时间最好只有一个部门真正修改代码**。

### 原则 3：每个部门结束都要输出摘要

每次都要求部门最后输出：

```text
同步给项目总控的摘要：
1. 本次做了什么
2. 发现了什么问题
3. 建议下一步做什么
4. 是否修改了文件
5. 如果修改了，修改了哪些文件
6. 需要项目总控决策的问题
```

### 原则 4：改代码前先由项目总控确认

不要让任何部门自己决定大改范围。

### 原则 5：验证部尽量提前介入

每次准备改代码前，先让验证部说明：

- 改前要跑什么检查
- 改后要跑什么验证
- 要做哪些手动测试

## 3. 推荐使用顺序

### 第 1 步：先用 `DailyTodo｜项目总控`

第一阶段不要急着改代码，先做整体理解和总规划。

建议发送：

```text
请开始 DailyTodo 规范化第 1 阶段：整体项目理解和总规划。

要求：
1. 先只理解项目，不改代码
2. 扫描项目结构、README、SPEC、package.json、src、electron、scripts、docs
3. 梳理产品定位、功能地图、技术栈、目录结构、主进程/渲染进程/数据层关系
4. 梳理任务系统、Obsidian 集成、AI Review、设置系统、验证体系
5. 输出项目理解报告
6. 输出后续各部门对话应该分别做什么
7. 最后给我一个可以同步给其他对话的项目总控摘要
```

### 第 2 步：让分析型部门先工作

推荐先用：

- `DailyTodo｜产品PMO`
- `DailyTodo｜工程效能部`
- `DailyTodo｜验证部`

它们先做分析，不改代码。

### 第 3 步：再让专业模块部门分析

按需要使用：

- `DailyTodo｜前端部`
- `DailyTodo｜桌面主进程部`
- `DailyTodo｜数据业务部`
- `DailyTodo｜设置系统部`
- `DailyTodo｜Obsidian集成部`
- `DailyTodo｜AI Review部`
- `DailyTodo｜视觉设计部`
- `DailyTodo｜文档部`
- `DailyTodo｜发布部`

### 第 4 步：回到项目总控汇总

把各部门摘要都贴回项目总控，让它制定实施路线图。

### 第 5 步：开始小步执行

由项目总控指定：

- 哪个部门执行
- 改哪些文件
- 不改哪些文件
- 要跑哪些验证

- 每个阶段开始前

## 5. 给各部门发消息的模板

## 模板 A：让部门做只读分析

```text
这是项目总控给你的背景摘要：

【粘贴项目总控摘要】

请你只做分析，不改代码。

目标：
1. 分析你负责的范围
2. 说明当前问题
3. 给出规范化建议
4. 标出风险点
5. 最后输出「同步给项目总控的摘要」
```

## 模板 B：让部门小步改代码

```text
这是项目总控分派给你的任务：

【粘贴任务描述】

要求：
1. 先说明修改计划
2. 只修改本次指定范围
3. 不碰未授权模块
4. 小步修改
5. 改完运行相关验证
6. 最后输出「同步给项目总控的摘要」
```

## 模板 C：把部门结果回传项目总控

```text
这是【某部门】的阶段摘要：

【粘贴摘要】

请你：
1. 合并到总规划
2. 判断是否影响当前规范化路线
3. 决定下一步应该派给哪个部门
4. 给我下一步可复制的提示词
```

## 6. 推荐的实际工作流

### 第一轮：全局理解

只用：

- `DailyTodo｜项目总控`

### 第二轮：三部门并行分析

推荐：

- `DailyTodo｜产品PMO`
- `DailyTodo｜工程效能部`
- `DailyTodo｜验证部`

说明：这一轮尽量只分析，不改代码。

### 第三轮：模块专项分析

再按需要调用：

- 数据业务部
- 前端部
- 桌面主进程部
- 设置系统部
- Obsidian集成部
- AI Review部
- 视觉设计部
- 文档部
- 发布部

### 第四轮：项目总控汇总

让项目总控输出：

- 实施路线图
- 优先级
- 风险等级
- 各任务负责部门
- 各任务验证方式

### 第五轮：开始执行

一次只让一个部门真正改代码。

---

## 7. 绝对不要这样用

不要这样：

```text
前端部正在改 App.tsx
设置系统部同时改 SettingsPanel.tsx
视觉设计部同时改 globals.css
AI Review部同时改报告页面
```

这种并发修改很容易冲突。

也不要这样：

```text
帮我把整个项目一起规范化并全部重构
```

正确方式是：

```text
一次一个目标
一次一个部门
一次一个小范围
每次都回到项目总控汇总
```

---

## 8. 一句话总结

这套对话的正确使用方式是：

```text
项目总控定方向
产品PMO定功能
工程效能部定结构
验证部定测试
各专业部门小范围分析或执行
所有结果回传项目总控
项目总控再安排下一步
```

如果不知道先做什么，就永远先打开：

- `DailyTodo｜项目总控`
